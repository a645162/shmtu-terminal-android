# 账单同步

账单同步是海大终端的核心功能，负责从校园一卡通系统拉取消费记录并存储到本地。

## 同步流程

整个同步流程如下：

1. 检查本地是否有有效登录会话（Cookie）
2. 如果会话过期，触发 CAS 登录
3. CAS 登录时下载验证码 → 识别验证码 → 提交登录
4. 登录成功后，请求账单数据
5. 解析账单页面，提取消费记录
6. 写入本地 Room 数据库（按 `transactionNo` 去重）

## 增量同步

增量同步只拉取自上次同步以来的新记录：

- 查询本地数据库中最新一条记录的时间
- 以该时间为起点，向后拉取新数据
- 速度快，流量消耗小
- **适合日常使用**

增量同步采用 `OnConflictStrategy.IGNORE` 策略，按交易号去重，即使重复调用也不会产生重复数据。

## 全量同步

全量同步从最早记录开始拉取所有历史数据：

- 从系统可查询的最早时间开始
- 逐页拉取直到当前时间
- 速度较慢，消耗流量较多
- **适合首次使用或数据补齐**

::: tip
首次使用建议先做一次全量同步，之后日常使用增量同步即可。
:::

## 单账号同步 vs 身份同步 vs 全部同步

- **单账号同步**：只同步当前选中账号的账单
- **身份同步**：同步某个身份下所有账号的账单（`SyncIdentityBillsUseCase`），适合一个身份下有多个账号的场景
- **全部同步**：遍历所有身份下的所有账号，依次触发同步

每个账号的同步是独立的，互不影响。一个账号同步失败不会影响其他账号。

## 账单分类

同步下来的消费记录会自动进行分类，由 `BillClassifier` 基于规则文件处理：

- **交易类型分类**（`type.json`）：区分消费、充值、补助等
- **消费地点分类**（`position.json`）：识别食堂、超市等具体商户
- **时间段分类**（`schedule.json`）：标注早餐、午餐、晚餐等时段

分类信息用于账单明细的展示和账单统计页面的数据聚合。

## 每账号独立数据库

应用为每个账号/身份创建独立的 Room 数据库实例，通过 `BillDatabaseManager` 动态管理：

- 数据库存储在各自的文件中
- 使用 `ConcurrentHashMap` 管理数据库实例的内存引用
- 避免不同账号的数据混在一起
- 删除账号时可以彻底清除对应数据库文件

## 同步失败的常见原因

| 原因 | 现象 | 解决方法 |
|------|------|----------|
| 密码错误 | 登录失败 | 检查并重新输入密码 |
| 验证码识别错误 | 登录失败 | 切换到手动输入模式，或重新配置 OCR |
| 网络问题 | 请求超时 | 检查网络连接，确保能访问校园网 |
| CAS 系统维护 | 页面返回异常 | 稍后重试 |
| Cookie 过期 | 需要重新登录 | 正常现象，应用会自动处理 |

## CAS 认证机制

所有校园系统（E-pay 账单、热水查询）都通过 CAS 统一认证：

1. 访问业务系统 → 系统返回 302 重定向到 CAS 登录页
2. 获取 `execution` 令牌和验证码
3. 提交学号、密码、验证码和 `execution`
4. CAS 验证通过 → 302 重定向回业务系统并携带 Ticket
5. 业务系统用 Ticket 建立会话

::: warning
`execution` 令牌是一次性的，必须在提交登录前即时获取，不能提前缓存。验证码下载和登录提交必须使用同一个 `JSESSIONID` Cookie 会话。
:::

应用使用 `OkHttpClient` 并设置 `followRedirects(false)`，手动处理 302 重定向链，确保 Cookie 和 Ticket 正确传递。
